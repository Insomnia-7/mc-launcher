## 结论与范围

现有 .NET 10 / WPF、四层划分、IJavaLocator / IDownloader 等抽象可以继续使用，本轮不更换框架、不增加 NuGet 依赖，也不调整实例和账号的数据格式。

本轮扫描了 src、tools、tests 中的源码风险写法，并深入检查 Java 发现、进程启动、下载与续传、导入回滚、备份导出、更新器、元数据缓存、模组管理及主界面任务控制。其他模块做了结构和调用检查，不能据此认定每个协议或加载器都已完成逐行审计和真实联网验收。

## 已完成的优化

| 项目 | 原问题 | 本轮处理 |
|---|---|---|
| Java 探测 | 每次发现都会重新启动 JVM；启动进程还单独探测一次 argfile 支持，旧实现先同步读完输出再等待，超时不能覆盖读流阶段 | JavaLocator 按可执行文件大小、修改时间及 release 文件时间缓存 2 分钟，同路径并发探测共用结果；目录扫描放到线程池；5 秒限制覆盖进程和标准输出读取；WinProcessLauncher 复用同一个探测器 |
| Java 兼容性 | 探测取消被当成没找到 Java；损坏 exe 的 Win32 错误可能中断发现 | 用户取消继续向上传播，损坏候选跳过；保留 PATH java 命令和 Java 8 直接参数模式 |
| 下载计数 | 跳过数与下载数各自作为 CompletedFiles，混合下载时结果不准确；跳过字节计入 DownloadedBytes | 分开完成进度与下载文件字节数，完成后发送最终一致的进度 |
| 下载分配 | 每个文件分配一块 80 KiB 缓冲并单独调度看门狗任务 | 使用 ArrayPool 复用传输缓冲；异步看门狗直接运行，保留原并发双重限制和停滞检测 |
| 断点续传 | 完整 .part 文件可能一直得到 416；未核对 206 的实际偏移 | 完整断点先校验后就位；416 和错误偏移清理无效断点后重试；保留正常 206 与服务器忽略 Range 的 200 行为 |
| 下载路径 | 直接 Path.Combine 可能接受整合包下载列表中的越界路径 | 复用现有 LongPath.Combine，拒绝绝对下载目标；新增越界不写盘、不发请求检查 |
| 导出备份 | 开始时先删旧备份，取消或读文件失败后旧备份丢失；输出在实例内部时可能把归档本身打进去 | 写唯一临时文件，成功关闭压缩包后才替换目标，失败保留旧备份并清理临时文件；排除输出自身；主界面导出的取消令牌真正接通 |
| 导入回滚 | 无法读取原目录清单时当成空清单，之后可能把原目录当新增目录删除 | 区分缺失目录、空清单与未知清单；未知清单对应的根目录不进行推断删除 |
| 更新器 | 注释承诺失败回滚，实际只备份与顺序复制，后续失败会留下混合版本 | 新增 Application.Update.UpdateFileTransaction：每个文件先备份、通过同目录临时文件替换；后续失败按逆序恢复，清除本次新增文件；回滚也失败时明确报告备份位置，日志保留真实结果 |
| 更新清单 | 先检查路径再替换反斜杠，可能漏掉反斜杠开头的根路径；重复目标可能重复替换 | 先统一分隔符，再检查根路径与别名；拒绝大小写或分隔符造成的重复目标 |

DownloadedBytes 表示本次完成下载的文件字节数，不再含直接跳过的文件；它不是网卡流量统计，已恢复的完整断点仍计入完成下载文件的大小。

## 性能实测

在同一 JavaLocator 实例、同一台开发机上发现 13 个 Java：

| 执行 | 耗时 |
|---|---:|
| 第一次扫描与探测 | 447.23 ms |
| 第二次扫描，探测缓存有效 | 22.94 ms |
| 第三次扫描，探测缓存有效 | 25.27 ms |

这测量的是 Java 发现，不是整个启动器冷启动或 Minecraft 主菜单时间。文件变化、缓存过期和进程重启仍需要重新探测。基准工具位于被忽略的 scratch/optimization-bench/，没有把机器路径和探测产物放进仓库。

## 审查时尚待处理的具体发现

> 更新：以下六项工程问题已在后续开发中处理，见 [修复交接](followup-fixes-2026-10-23.md)。下文保留原始审查发现供对照。

### P1：模组更新需要事务保护

MainViewModel.ApplyModUpdateAsync 仍先 File.Delete(oldPath)，再安装新版本。下载或前置解析失败时旧模组可能丢失；新主文件下载成功但依赖失败时，还要考虑新旧文件混存。

建议先在独立目录完成新文件和依赖的准备，验证后提交替换，失败恢复原模组集合。仅把旧文件改名后直接下载还不够，因为新文件名可能不同。此项需要覆盖新文件名、同名覆盖、依赖失败、取消与 CF 来源，不在本轮顺手改写。

### P1：跨页面写任务应共用互斥规则

MainViewModel 与 DownloadViewModel 各自维护 IsBusy。主界面导入和下载中心安装可能写入同一游戏根目录；ImportTransaction 的目录差集也无法判断另一个并发任务新建目录的归属。

本轮向导和导出入口会检查下载页状态，但所有写任务仍需要统一的互斥或明确的目录所有权记录。建议在用例层引入共享任务协调，保持当前 UI 和接口职责。

### P2：模组来源信息不足

ModUpdateService 使用 jar 内的 mod.ModId 请求平台项目版本，jar 的 modId 与平台项目 ID / slug 不保证相同。

建议安装时记录平台、项目和文件 ID，导入包保留来源映射；本地手工放入的文件再通过明确的匹配流程补信息。

### P2：元数据缓存可以合并并发请求并改善 IO 容错

MojangMetaClient.GetManifestAsync 没有合并同一时刻的请求，磁盘写缓存共用固定 .tmp 文件；ReadCacheAsync 主要处理 JsonException，读取失败的 IOException 仍可能影响本可在线获取的元数据。

建议单个键共用正在执行的请求、唯一临时文件写入、缓存读取错误降级为未命中，并保持用户取消语义。

### P2：模组元数据缓存与扫描的边界处理

ModFileGuard.ReadMetadata 在 try 块外读取 FileInfo.Length；扫描与删除并发时会抛文件不存在。缓存键包含每次修改时间，旧版本条目不会被替换回收。

建议将 stat 放入容错区域，并按文件路径保存最新指纹和结果。

### P2：重复 classpath 构建可以在测量后合并

LaunchPreparer、LaunchPreflight 与 LaunchPlanBuilder 都会构建 classpath。可以把一次准备结果传给后两者，避免重复规则计算和文件查询，但应保留单独调用接口，先测收益再改动。

### 发布前仍需独立设计

更新清单签名、签名密钥管理和更新器自更新生命周期仍未解决。当前更新事务只处理进程运行期间的异常恢复，不承诺断电或被强制结束后自动回滚；如要保证该场景，需要持久化事务日志和恢复入口。

多账号 UI、许可证选择、CurseForge 搜索权限等产品和发布事项沿用原交接清单，未混入本轮底层优化。
