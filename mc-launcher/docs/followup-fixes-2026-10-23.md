# 审查问题修复交接 · 2026-10-23

本轮继续在 `<repository>/mc-launcher` 开发，完成上一份审查中列出的六项工程问题。沿用 .NET 10 / WPF、现有分层和依赖，没有新增 NuGet 包。

## 六项处理结果

| 原问题 | 现在的行为 |
|---|---|
| 模组更新先删除旧文件 | Modrinth / CurseForge 均先解析选定版本及必需前置，在独立目录下载和校验，再提交主文件、依赖和来源索引。提交失败恢复原文件集合，下载失败不动旧文件；支持同名、新文件名和已禁用模组。 |
| 跨页面写任务不互斥 | Application 中的 GameOperationCoordinator 按游戏根目录协调写任务。主界面、下载页和安装向导共用它；不同根目录与只读查询可并行，冲突显示当前任务。 |
| 内部 modId 被当成平台 ID | 安装时记录真实平台、项目、版本/文件 ID 和实际 SHA-1；检查更新先验证来源与文件一致。手工放入或旧实例没有记录时，用 Modrinth 文件哈希确认所属项目；无法匹配则提示不可确认更新。 |
| 元数据缓存并发与 IO 错误 | 同一键共用串行刷新与缓存结果，覆盖 manifest、版本和资源索引；唯一临时文件写入。损坏、占用或不可写的磁盘缓存退化为未命中，失败结果不缓存，取消保留原语义。 |
| 模组元数据缓存边界 | FileInfo 与 jar 读取统一置于容错范围；同一路径只保留最新大小、时间和解析结果。删除或临时占用不导致扫描崩溃，临时失败不固化为空缓存。 |
| 重复构建 classpath | LaunchPreparation 保存本次计算结果，App 和 CLI 将其传给预检、计划构建。保留原来的独立调用入口。 |

准备依赖时保留普通安装的原有容错，事务更新使用严格准备：必需前置解析失败或指定前置版本不存在时停止，不提交半套更新。已有前置与明确指定的版本冲突时提示先处理前置，保留原集合；不自动推测兼容性或改写整个整合包。

同时修正了两个相关调用问题：下载页现在使用所选实例 ID，避免第二实例误写共用版本的目录；并发更新检查结束后发送一致的 100% 进度，避免最后一条进度回退。

## 文件与数据

- 每个资源目录新增 `.launcher-sources.json`，记录实际文件对应的平台身份和哈希，不保存账号令牌。
- CurseForge 包导入保留清单中的项目与文件 ID；Modrinth 包保留哈希线索。overrides 改写内容后，不绑定不匹配的来源。
- 模组更新暂存目录：`instances/<实例>/.launcher-staging/<随机目录>/`，正常完成或失败后清理。
- 原文件备份：`instances/<实例>/.launcher-backup/<随机目录>/`，保留供恢复，不自动删除历史备份。
- 实例、账号和设置的原有文件格式不变。来源侧车文件会随实例内容一起导出。
- 任务互斥作用于启动器进程内的页面和任务，不是跨进程文件锁。

主要代码：

- `Application/Mods/ModUpdateInstaller.cs`：更新编排与暂存校验。
- `Application/Mods/ModSourceStore.cs`：来源记录、实际文件匹配及普通安装共用执行。
- `Application/Operations/GameOperationCoordinator.cs`：写任务互斥。
- `Infrastructure/Meta/MojangMetaClient.cs`：元数据请求与缓存。
- `Application/Mods/ModFileGuard.cs`：jar 元数据缓存。
- `Application/Launch/LaunchPreparation.cs`：本次启动准备结果复用。
- `tests/Core.Checks/FollowupChecks.cs`：本轮故障与兼容检查。
