# 内存、模组与安装存储调整

当前批次：1.0.0-preview.24。开发与验收优先面向 Windows，保留未来 Linux、macOS 接入结构。

## 内存选择

实例设置与安装向导使用同一套“自动分配 / 自定义滑块”，每格 512 MiB，不再要求输入内存数值。显示系统已用、游戏分配和预计剩余的分段条；系统占用可刷新，分配过高时给出提示。

新实例默认自动分配，沿用本机物理内存四分之一、2–16 GiB 范围的既有策略，启动时重新计算。自动模式单独持久化，旧配置中明确写入的数值保留为自定义，不会擅自改成自动。最大堆大小以保存后的设置为准，实际 Java 进程还会使用堆外内存，因此“剩余”是估算。

## 实例与公共依赖

加载器继承的原版版本仍保留在 versions 中供启动使用，但不再作为一条多余的虚拟实例显示。明确安装纯原版时写入独立实例元数据；已有真实实例和旧版任务记录中明确选择过的原版仍保留。

同一游戏库内的 assets、libraries 和版本文件继续共享；模组、配置和存档落在实例私有目录。行为参考 [HMCL 版本隔离文档](https://docs.hmcl.net/launcher/isolation.html)，以及 [PCL 关于压缩管理卡片、保留功能按钮与模组状态的更新记录](https://github.com/Meloong-Git/PCL/discussions/2908)。

## 整合包与下载暂存

原故障有两条路径：任务工作目录在启动器数据盘、目标实例在游戏盘时，目录移动不能跨卷；Windows 长短路径一边带扩展前缀、一边不带前缀时，目录移动也可能被判为根不同。

- 新任务的大体积文件放在游戏库的 `.cache/tasks/<任务编号>`，导入暂存位于其 import 子目录，提交目录时保持同一游戏盘和一致的 Windows 路径形式。
- 任务记录仍位于启动器数据目录的 task-center，单独保存小型 JSON；旧任务保留原下载包以便恢复，整合包提交改用游戏盘暂存，完成或取消会清理新旧两处暂存。
- 已经不存在的断点文件视为清理完成，兼容 Windows 长路径记录。已经安装完成、只剩缓存被占用时保持“已完成”并说明清理问题，不误报游戏安装失败。
- 需要恢复原文件的备份不会被取消或缓存清理删除，任务保留明确的恢复状态；暂停、失败任务的断点保留，成功后才清理临时文件。
- 存储页分别统计游戏下载暂存、旧版暂存、公共资源、公共运行库、版本文件及实例，避免重复计算。可以回收已结束任务及超过七天的无记录暂存；存档、完整公共资源和手动备份不作为垃圾删除。

## 逐文件 Mod 管理

实例页增加“管理模组”直达入口。列表可按名称、元数据与文件名搜索；每行可查看路径、大小、修改时间与 SHA-1，打开文件位置，启用 / 停用，以及确认后永久删除单个文件。删除前明确告知文件与永久删除行为，取消不改动文件；游戏运行期间禁止修改。

单个文件操作复用已有事务、哈希校验和任务记录。启停可逆，不再每次复制整包快照；单文件永久删除也不复制整个整合包。原有批量删除及更新前快照继续保留。单文件成功直接在列表反馈，不连续叠加成功弹层遮挡操作；失败仍提示原因。

列表采用有界滚动视口与可见行虚拟化，避免大量模组时一次创建全部行控件。保留兼容更新、版本锁定、批量操作和试装副本功能。

## 分阶段验收

- M0：复现并定位跨盘 / 长路径目录提交及清理误报。
- M1：验证任务暂存、取消、暂停恢复、旧目录兼容与恢复资料保留。
- M2：验证原版依赖隐藏、明确安装原版仍可见，且不删除启动依赖。
- M3：验证自动内存、自定义滑块、设置保存和系统占用展示。
- M4：验证 Mod 详情、定位、启停、删除确认、搜索及长列表滚动。
- M5：验证透明启动图标仅剩图标，原有入场动画及小窗口深浅主题保持可用；记录 Windows 优先范围，停止 Unix 自动预览构建。
- M6：执行核心、架构与相关 UI 回归，使用实际发布程序集及真实单文件验证，签名更新并从公开下载入口复核。

所有验收使用 D 盘隔离数据与合成账号；不访问或清理用户真实游戏库、存档和账号令牌。真实用户整合包、账号进入世界及其他物理设备的验收不能由夹具代替；最终已通过范围以 verification.json 为准。
