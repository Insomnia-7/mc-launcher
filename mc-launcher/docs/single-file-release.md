# 单文件发布落地

## 交付形态

框架依赖的 Windows x64 单文件程序，内嵌独立更新器。需要 .NET 10 Desktop Runtime；源码开发构建继续支持多文件布局，没有更换框架或引入新的运行时依赖。项目开发版本为 0.1.2；本轮不创建发布标签或公开 Release。

本地命令（从仓库根目录执行）：

```powershell
pwsh -File scripts/publish-launcher.ps1
```

默认输出 `mc-launcher/dist/portable/MCLauncher.exe`。可以指定 `-OutputDirectory` 和 `-Version`，输出目录必须为空。脚本优先使用 DOTNET_ROOT 中的 SDK，否则使用 PATH 中的 dotnet。

## 更新器与发布顺序

单文件构建要求 UpdaterPayload 指向真实存在的已发布更新器，缺少它会明确停止构建。更新器的单文件产物作为程序集资源内嵌，普通构建不受此限制。

更新时优先提取内嵌更新器，避免旧的 updater 目录抢先被使用。缓存位于数据目录 `cache/update-helper/<SHA-256>/mclupd.exe`，缓存内容与资源完整哈希一致才复用；长度相同的损坏文件也会重写。提取失败通过原更新错误提示反馈，不让异常落出命令处理。

更新器运行位置位于目标安装目录之外，替换主程序时不会锁住旧的 updater 文件。更新器的内置公钥随新主程序内嵌资源一起升级，单文件版本后续不需要单独替换外置更新器。缓存和 `.backup` 是有意保留的数据，不属于发行包附带的独立文件。

GitHub Actions 顺序：回归检查 → 发布更新器到 payload → 可选 Authenticode 签更新器 → 发布并内嵌到主程序 → 可选签主程序 → 单文件布局校验 → 便携 ZIP → 更新清单 → 清单签名与独立验签 → 上传。

代码签名证书仍仅在相应步骤注入；没有证书时保留既有提示。证书签名顺序保证内嵌的是签过的更新器，文件哈希在所有签名完成后计算。实际证书尚未配置，本轮不宣称消除 SmartScreen 提示。

## 迁移与回滚

已具备 installed-files.json 账本的多文件安装，可以在更新后将旧的发布文件移入 `.backup/<时间戳>/`，保留用户自行添加的文件。没有账本的旧安装不猜测哪些文件可删除，首次迁移建议完整安装新包并保留原目录备份。

旧 v0.1.0 / v0.1.1 无法获得追溯性的签名保护。轮换公钥仍应先发布由旧密钥签名、同时内置新旧公钥的过渡版本，再切换私钥。此后单文件主程序和内嵌更新器会同步携带信任目录。

需要回滚时先关闭测试或实际启动器，将备份中的旧程序及依赖完整恢复；不要只恢复某一个 DLL。多文件构建入口仍保留，未来可按需要恢复发行布局。

- 完整 Release 构建零错误、零警告。
- 594 项核心检查通过，其中新增 8 项内嵌更新器提取、缓存校验、损坏修复、空资源与占用失败检查。
- 90 项 WPF 检查通过；分别验证普通构建的外置更新器定位和携带真实资源时的内嵌优先、哈希一致。架构检查通过。
- 实际发布的单 EXE 约 2.4 MB；这是框架依赖包大小，不包含目标机预装的桌面运行时。
- 实际完成 18 文件 → 单 EXE 的签名迁移：新旧程序哈希不同；更新器等待旧进程退出；17 个旧发布文件清理并完整备份；用户测试文件保留；账本只剩新 EXE；新程序自动重启并呈现响应窗口。
- 缺少 UpdaterPayload 的构建被明确拒绝，避免生成无法自更新的单文件。

端到端测试工具为仓库根 `scripts/check-single-file-update.ps1`。传入旧发布目录、新单文件目录、已发布更新器、仓库外签名密钥备份和空测试目录即可复现；只关闭本测试启动的进程。测试签名在本机进行，不读取或输出 GitHub Secret。

本轮未创建新 Release、没有运行 GitHub 的实际签名发布；未重新做完整游戏下载、正版登录或皮肤联网验收。窗口响应验证不等同于完整冷启动性能基准。旧方案目录中的首帧测量属于历史实验，本轮不复用为新的性能结论。
